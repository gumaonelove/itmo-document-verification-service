# itmo-document-verification-service

**ВериДок** — локальный сервис проверки достоверности корпоративных документов. Практика ИТМО, 1 курс, 2 семестр (MVP).

## 1. Что это

ВериДок принимает проверяемый документ (PDF/DOCX/PPTX) и набор доверенных источников, извлекает из документа отдельные утверждения (числа, даты, имена, факты) и для каждого выносит вердикт: подтверждено источниками (`supported`), опровергнуто (`contradicted`), не найдено (`not_found`) или противоречит другому утверждению того же документа (`internal_conflict`). Каждая находка несёт ссылку на местоположение в документе (страница/слайд/абзац). Всё работает локально, без облачных API; интерфейс и документы — на русском. Все вызовы LLM выполняются при `temperature=0.0` для воспроизводимости.

**В scope:** парсинг PDF/DOCX/PPTX; извлечение атомарных утверждений через LLM; индексация источников в Qdrant и поиск по эмбеддингам; верификация по найденным фрагментам; проверка внутренней согласованности; отчёт в Streamlit и CLI.

**Вне scope:** облачные/внешние LLM-API; OCR сканов и изображений; обучение/дообучение моделей; аутентификация, многопользовательский режим, постоянное хранилище отчётов; форматы, кроме PDF/DOCX/PPTX.

## 2. Архитектура

Поток данных: источники индексируются в Qdrant; проверяемый документ проходит конвейер parse → extract → retrieve → verify; параллельно проверяется внутренняя согласованность; результат собирается в отчёт и отображается в Streamlit (или в консоли через CLI).

```
  ДОВЕРЕННЫЕ ИСТОЧНИКИ                       ПРОВЕРЯЕМЫЙ ДОКУМЕНТ
  (pdf / docx / pptx)                        (pdf / docx / pptx)
          │                                          │
          ▼                                          ▼
       parse                                       parse
   (PyMuPDF4LLM /                              (PyMuPDF4LLM /
    python-docx /                               python-docx /
    python-pptx)                                python-pptx)
          │                                          │
          ▼                                          ▼
    чанкинг + эмбеддинг                          extract
   (sentence-transformers)                  (LLM → утверждения:
          │                                  number/date/name/statement,
          ▼                                  каждое с location)
   ┌──────────────┐                               │
   │    QDRANT    │◀───── retrieve (top_k) ───────┤
   │ (коллекция   │       embed_query(claim)      │
   │  векторов)   │──────► evidence ──────────────┤
   └──────────────┘                               ▼
                                                verify
                                            (LLM по claim+evidence →
                                             supported / contradicted /
                                             not_found)
                                                  │
                            consistency           │
                       (LLM по всем claims ───────┤
                        → internal_conflict)       │
                                                  ▼
                                               Report
                                       (findings + stats + время)
                                                  │
                                ┌─────────────────┴─────────────────┐
                                ▼                                   ▼
                         streamlit run app.py            python -m veridoc.pipeline
                         (таблица + раскраска)            (таблица в консоли)
```

Если источники не предоставлены, все утверждения помечаются `not_found`, но проверка внутренней согласованности всё равно выполняется.

## 3. Стек

Система **модель-агностична**: LLM подключается по OpenAI-совместимому HTTP, смена модели — это смена `LLM_MODEL` (и при необходимости `LLM_BASE_URL`), код пайплайна не меняется.

- **LLM:** любая модель по OpenAI-совместимому эндпойнту (`LLM_BASE_URL`/`LLM_MODEL`, через `openai` SDK). **Реально прогонялись локально через Ollama:** `qwen3-coder:30b` (модель по умолчанию — лучший результат на корпусе оценки) и `T-lite-it-2.1` (T-Tech; лёгкая русско-специализированная альтернатива); **GigaChat 3 Lightning** — поддерживается той же сменой `LLM_MODEL` (см. §9 и `.env.example`). Сравнение моделей — в [eval/MODEL_COMPARISON.md](eval/MODEL_COMPARISON.md).
- **Эмбеддер:** **Qwen3-Embedding-8B** (dim `EMBED_DIM=4096`). Бэкенд: `ollama` (`qwen3-embedding:8b`, по умолчанию) либо `sentence-transformers` (`Qwen/Qwen3-Embedding-8B`, `device=mps`) — это одна и та же модель.
- **Векторное хранилище:** **Qdrant** — сервер (docker) или embedded (on-disk). Коллекция пересоздаётся на каждую проверку (поиск не подмешивает чужие документы).
- **Парсинг:** PyMuPDF4LLM (PDF; `import pymupdf` / `fitz`), `python-docx` (DOCX), `python-pptx` (PPTX).
- **UI:** Streamlit. **Конфигурация:** `pydantic-settings` (`config.py`, читает `.env`).

## 4. Установка

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env   # при необходимости отредактируйте значения
```

### Подъём LLM

Нужен любой локальный OpenAI-совместимый раннер. По умолчанию — **Ollama** с моделью `qwen3-coder:30b`; смена модели — это смена `LLM_MODEL`:

```bash
LLM_BASE_URL=http://localhost:11434/v1
LLM_MODEL=qwen3-coder:30b   # или hf.co/t-tech/T-lite-it-2.1-GGUF:latest, GigaChat-тег, …
LLM_API_KEY=ollama
```

Локальные серверы обычно игнорируют ключ, но `openai` SDK требует непустое значение. Эмбеддер тоже идёт через Ollama (`EMBED_BACKEND=ollama`, `qwen3-embedding:8b`) — отдельная загрузка модели не нужна.

### Qdrant

Вариант 1 — сервер в Docker:

```bash
docker run -p 6333:6333 qdrant/qdrant
```

и в `.env` оставьте `QDRANT_URL=http://localhost:6333`.

Вариант 2 — embedded (on-disk), без отдельного сервиса: задайте в `.env` путь к каталогу данных:

```bash
QDRANT_PATH=./qdrant_data
```

Если `QDRANT_PATH` задан, используется embedded-режим, а `QDRANT_URL` игнорируется.

## 5. Запуск

UI (Streamlit): загрузите проверяемый документ и источники, нажмите «Проверить».

```bash
streamlit run app.py
```

CLI: печатает таблицу находок и сводку по вердиктам в консоль.

```bash
python -m veridoc.pipeline <документ> --sources <папка_источников>
```

Например:

```bash
python -m veridoc.pipeline report.pdf --sources ./sources
```

Флаг `--sources` необязателен: без него выполняется только проверка внутренней согласованности.

## 6. Оценка

Сначала сгенерируйте корпус (детерминированно, по `--seed`), затем посчитайте метрики на реальных прогонах:

```bash
python eval/seed.py --docs 16 --numeric 2 --claim 2 --internal 2     # корпус → eval/datasets/
python eval/evaluate.py --manual-min-per-doc 25                       # qwen3-coder:30b (модель по умолчанию)
LLM_MODEL=hf.co/t-tech/T-lite-it-2.1-GGUF:latest python eval/evaluate.py --manual-min-per-doc 25 \
    --model T-lite-it-2.1 --results eval/results_t-lite.json          # другая модель — одной сменой LLM_MODEL
cat eval/results/metrics.md
```

`seed.py` параметризуется числом документов и ошибок каждого типа (`--numeric/--claim/--internal/--notfound/--clean`), генерирует все три формата (DOCX/PPTX/PDF) и записывает машиночитаемый манифест `eval/datasets/ground_truth.json`.

`evaluate.py` прогоняет `run_check` по каждому документу и пишет артефакты:
- [eval/results.json](eval/results.json) — метрики и пер-документная разбивка;
- [eval/results/metrics.md](eval/results/metrics.md) — финальная таблица для слайдов (общие метрики + по типам и форматам + время + ускорение vs ручная);
- [eval/errors.csv](eval/errors.csv) — TP/FP/FN с локациями.

Числа получаются **только реальными прогонами**; при недоступном LLM-эндпойнте `run_check` падает с понятной ошибкой (заглушек нет). Все вызовы LLM — при `temperature=0`.

## 8. Важные замечания

- **Эмбеддер Qwen3-Embedding-8B, два бэкенда.** По умолчанию `ollama` (`qwen3-embedding:8b`); альтернатива — `sentence-transformers` (`Qwen/Qwen3-Embedding-8B`, `device=mps`). Не через `mlx-lm` (он не поддерживает embedding-модели). LLM и эмбеддер — разные подсистемы.
- **Запросные эмбеддинги идут с инструкцией.** Запросы кодируются с `prompt_name="query"` (документы — без инструкции). Если модель не зарегистрировала этот prompt, эмбеддер автоматически добавляет ручной префикс `Instruct: ...\nQuery: `.
- **Смена `EMBED_DIM` пересоздаёт коллекцию Qdrant.** При расхождении размерности существующей коллекции с настроенной она удаляется и создаётся заново — переиндексируйте источники.
- **Бюджет памяти ~M4 Max 48 GB.** Индексация источников и верификация документа — разные фазы; держите их раздельно, чтобы не превышать память (LLM и эмбеддер крупные).
- **Фолбэки моделей.** Если штатный `prompt_name="query"` недоступен, используется ручной префикс инструкции (см. выше). Имена модели LLM и эмбеддера задаются через `.env` — при отсутствии конкретного тега замените на доступный совместимый.
- **Воспроизводимость.** Все вызовы LLM — при `temperature=0.0`.

## 9. Метрики оценки

Все числа — из **реальных прогонов** `eval/evaluate.py` (без заглушек). Источник истины — [eval/results/metrics.md](eval/results/metrics.md), [eval/results.json](eval/results.json) и [eval/errors.csv](eval/errors.csv). Корпус синтетический, генерируется детерминированно по `--seed` (повтор даёт тот же набор); все вызовы LLM при `temperature=0`.

### Правило сопоставления (как находка засчитывается)

«Позитив» — находка с вердиктом `contradicted` или `internal_conflict`. Внесённая ошибка считается **пойманной (TP)**, если есть ещё не использованный позитив, у которого: **(а)** совпадает индекс локации (место утверждения ЛИБО место его evidence — для внутреннего конфликта это второе, конфликтующее утверждение) **или (б)** подменённое значение встречается в тексте находки/цитате/обосновании. Вердикт-метка точно совпадать не обязана (и `contradicted`, и `internal_conflict` — это детекция). Сопоставление жадное 1:1.

- **Дедуп двойного подсчёта:** если одно значение помечено и как `internal_conflict`, и как `contradicted` на одной локации — это **одна** детекция, а не ложное срабатывание.
- **`not_found` — отдельная диагностика** (НЕ входит в recall/precision): проверяем, что на «отсутствующих в источнике» фактах сервис не выдаёт ложный `contradicted`.
- **Чистые документы** (без ошибок): любой позитив на них — ложное срабатывание (FP).

### Результаты (модель по умолчанию — qwen3-coder:30b)

Корпус: **16 документов** (3 чистых), **78 внесённых ошибок** + 13 `not_found`-кейсов; форматы DOCX/PPTX/PDF; локально через Ollama, Qdrant в Docker.

| Метрика | qwen3-coder:30b (дефолт) | T-lite-it-2.1 (альтернатива) |
|---|---|---|
| Recall | **1.00** | 0.87 |
| Precision | **1.00** | 1.00 |
| F1 | **1.00** | 0.93 |
| Ср. время / документ | ~19 c | ~23 c |
| not_found (диагностика) | 13/13 | 13/13 |
| Ускорение vs ручная (~25 мин/док) | ×79 | ×66 |

По типам recall у qwen3-coder = 1.00 на всех (numeric/claim/internal) и по всем форматам; **ноль ложных срабатываний**, в т.ч. на чистых документах. Полные разбивки — в [eval/results/metrics.md](eval/results/metrics.md) (qwen, канонический) и [eval/results/metrics_t-lite.md](eval/results/metrics_t-lite.md).

**Ограничения (честно):** набор **синтетический** (N=16/78, фиксированный seed, шаблонные формулировки) — сильная модель закономерно достигает на нём потолка, поэтому **1.0 трактуется в этом контексте, а не как «идеально на любых документах»**. Более лёгкая T-lite-it-2.1 на том же наборе даёт 0.87 с прозрачной разбивкой (слабее на фактологических/именных противоречиях; извлечение названий организаций — известное ограничение). Полное сравнение — [eval/MODEL_COMPARISON.md](eval/MODEL_COMPARISON.md).
