# Сравнение моделей ВериДок

Все строки таблицы — **реальные прогоны** `eval/evaluate.py` на одном и том же
корпусе (`eval/datasets/`, seed=42: 16 документов, 78 внесённых ошибок + 13
not_found-кейсов, форматы DOCX/PPTX/PDF). Стек, кроме LLM, общий: эмбеддер
Qwen3-Embedding-8B, Qdrant. Все вызовы LLM при `temperature=0`. Система
модель-агностична — каждый прогон выполняется одной сменой `LLM_MODEL`.

Команда прогона (пример для второй модели):

```bash
# дефолт (qwen3-coder:30b) — канонические артефакты results.json/errors.csv/metrics.md:
python eval/evaluate.py --manual-min-per-doc 25
# альтернативная модель — одной сменой LLM_MODEL (в суффиксные артефакты):
LLM_MODEL=hf.co/t-tech/T-lite-it-2.1-GGUF:latest python eval/evaluate.py \
    --manual-min-per-doc 25 --model T-lite-it-2.1 --results eval/results_t-lite.json
```

## Полные прогоны (eval по всему корпусу)

| Модель | Recall | Precision | F1 | claim (recall) | internal | ср. время/док | Ускорение | not_found |
|---|---|---|---|---|---|---|---|---|
| **qwen3-coder:30b** (дефолт) | **1.00** | **1.00** | **1.00** | 1.00 | 1.00 | ~19 c | ×78 | 13/13 |
| **T-lite-it-2.1** (T-Tech) | 0.87 | 1.00 | 0.93 | 0.65 | 0.96 | ~23 c | ×66 | 13/13 |

Источники чисел: `eval/results.json` (qwen, канонический) и `eval/results_t-lite.json`
(T-lite). У обеих моделей `numeric` (числа/даты/проценты/суммы) = 1.00 и precision =
1.00 (ноль ложных срабатываний, в т.ч. на чистых документах).

**Вывод.** На расширенном корпусе **qwen3-coder:30b** показывает лучший результат
(идеальные recall/precision и выше скорость, MoE с ~3B активных параметров), в т.ч.
надёжно ловит фактологические/именные противоречия (`claim`), где T-lite слабее
(0.65) — поэтому qwen3-coder **выбрана моделью по умолчанию**. T-lite-it-2.1 — более
лёгкая русско-специализированная альтернатива с тем же нулём ложных срабатываний.
(Ранее, на маленьком наборе из 8 ошибок, ранжирование было иным — это показывает
ценность большего корпуса.) Набор синтетический (N=16/78), поэтому 1.0 — потолок на
этом наборе, а не «идеально на любых документах».

## GigaChat 3 Lightning — `pending`

Эндпойнт GigaChat в текущем окружении недоступен (модель не установлена в Ollama),
поэтому **числа не приводятся — чтобы не фабриковать**. Прогон выполняется ОДНОЙ
сменой `LLM_MODEL` после поднятия модели по OpenAI-совместимому API (см.
`.env.example`):

```bash
LLM_MODEL=<gigachat-3-lightning-тег> python eval/evaluate.py \
    --manual-min-per-doc 25 --model gigachat-3-lightning \
    --results eval/results_gigachat.json
```

После прогона строку GigaChat нужно внести в таблицу выше из
`eval/results_gigachat.json`.

## Модели, ломающие строгий JSON на этапе extract (быстрый отбор)

Помимо полных прогонов проверялась пригодность других локально доступных моделей
по строгости JSON на реальных промптах extract/verify/consistency. Следующие
**ломали строгий JSON на извлечении** (выдавали reasoning/markdown вместо чистого
массива) и потому не годятся без доработки парсинга: `qwen3.5:27b`, `qwen3-vl:30b`,
`gpt-oss:20b`. Чисто проходили: `qwen3-coder:30b`, `T-lite-it-2.1`, `gemma4:31b`
(но медленнее), `qwen2.5:7b` (путал типы). Это отбор по JSON-надёжности, а не полный
eval — полные метрики выше только для двух моделей, прогнанных по всему корпусу.
